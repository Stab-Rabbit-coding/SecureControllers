## Safety precedence — the rule that overrides everything else

SP 800-82r3 §4.2.2 treats safety systems as a special area of consideration, and §5.3.1
covers cyber-related safety considerations.  The operating rule for this skill:

**A security control may never be introduced in a way that defeats a safety function.**

Concretely, for a controller you are designing:

- A failed authentication must not silently disable a motor-stop path.
- A watchdog or brownout reset must not be preventable by a security lockout.
- Log-write latency must not extend the control-loop period past its deadline.
- Cryptographic operations must not run on the critical path of an emergency stop.
- A security lockout state must have a documented, safe exit.

Where the safety function and the security control genuinely conflict, the safety function
wins and the residual security risk is **documented and accepted**, not engineered away by
weakening safety.  ISA-TR84.00.09 (REF-ISA-TR84-00-09) is the technical report covering this
interaction; SP 800-82r3 App. D.1.5.4 lists it by designation and title.

The inverse trap is equally real: a safety argument is **not** a license to skip security.
"We can't authenticate the E-stop because it must always work" is a design problem to solve
(authenticate the *enable*, keep the *stop* unconditional), not a reason to leave a bus open.

## Where your board sits — Purdue / ISA-95

Reproduced from skill `18-ot-ics-security` for continuity of vocabulary:

| Level | Zone | Assets | Your board? |
| --- | --- | --- | --- |
| 4–5 | Enterprise / IT | ERP, business network, internet | No |
| 3.5 | IDMZ | Jump hosts, patch relays, historian replica | No |
| 3 | Operations | SCADA servers, historians, engineering WS | No |
| 2 | Supervisory | HMIs, control servers | GCS / autopilot may sit here |
| 1 | Control | PLCs, RTUs, IEDs | Flight controller, motion controller |
| 0 | Process | Sensors, actuators, drives | **Servo, ESC, sensor node** |

Most boards in this user's portfolio are **Level 0–1**.  SP 800-82r3 §5.3.6 addresses Field
I/O at Purdue Level 0 specifically, and §5.3.7 adds considerations for IIoT — which is the
right lens for a network-connected smart actuator, because it is simultaneously Level 0
equipment and an IoT product.

**The Level 0 problem:** historically, Level 0 was protected by being dumb and physically
inaccessible.  A smart servo with a CAN stack and firmware update is neither.  It has the
attack surface of a networked computer and the safety authority of a final control element.
That combination is why this skill exists.

## Defense in depth — SP 800-82r3 §5.2 layers on one board

The five DiD architecture layers of §5.2.1–5.2.5, and what each means at board scope:

| Layer | § | Board-level obligation |
| --- | --- | --- |
| 1 — Security Management | 5.2.1 | The SDLC, threat model, and vulnerability handling behind the board (→ 62443-4-1) |
| 2 — Physical Security | 5.2.2 | Conformal coat, potting, tamper-evident seals, test-point placement, enclosure |
| 3 — Network Security | 5.2.3 | Bus authentication, segmentation at the payload boundary, protocol hardening |
| 4 — **Hardware Security** | 5.2.4 | Secure element / TPM, readout protection, debug-port lifecycle, fuse map |
| 5 — Software Security | 5.2.5 | Secure boot, MPU/TrustZone, memory safety, input validation |

Layer 4 is the one a firmware-only review misses and the one that is unrecoverable after
fabrication.  **Hardware security decisions are gates at the ideation phase**, not
refinements later:

- Is there a hardware root of trust, and is it a real part with a real part number?
- Is flash readout protection available on the chosen MCU, and does enabling it brick the
  debug workflow the team depends on?
- Is there a physical tamper input, and is anything wired to it?
- Where are the test points, and are they on the outer layer where a probe reaches them?

## ISA/IEC 62443-4-2 — your board is an EDR

REF-ISA-62443-4-2 [19] defines four component types.  A microcontroller-based servo, ESC,
or flight-control node is an **Embedded Device (EDR)**.

The seven Foundational Requirements, with the board-level question each asks:

| FR | Title | Board question |
| --- | --- | --- |
| FR 1 | Identification and Authentication Control (IAC) | Can the board prove who it is, and verify who is talking to it? |
| FR 2 | Use Control (UC) | Once authenticated, what is this entity actually permitted to do? |
| FR 3 | System Integrity (SI) | Can the board detect unauthorized change to its code, config, and data? |
| FR 4 | Data Confidentiality (DC) | Is sensitive data protected at rest and in transit? |
| FR 5 | Restricted Data Flow (RDF) | Does the board enforce the zone/conduit boundary it sits on? |
| FR 6 | Timely Response to Events (TRE) | Does it log, alert, and let an operator act? |
| FR 7 | Resource Availability (RA) | Can it be starved, flooded, or wedged out of its control duty? |

**FR 7 is the one that is different for a controller.** In IT, availability loss is an
outage.  On a Level 0 actuator, availability loss is a runaway or a fall.  Test it
deliberately: bus flood, malformed frame storm, log-storage exhaustion, crypto-operation
queue saturation.  Verify the control loop still meets its deadline or fails safe.

> **Clause discipline.** The FR titles above are verified public information.  Individual
> component requirement numbers (CR 1.1, EDR 3.12, and so on) are **not** reproduced in this
> skill because no local copy of the standard was available.  If a design record needs a
> CR-level citation, obtain the standard and mark the REFERENCES.md entry verified first.
> Never write a CR number from memory.

## Security Levels — set a target before you design

REF-ISA-62443-3-3 [20] defines SL 0–4 by the capability of the adversary the system resists,
and distinguishes **SL-T** (target), **SL-A** (achieved), and **SL-C** (capability).

Rough guide for setting SL-T on a controller (authored, not normative):

| Context | Suggested SL-T | Reasoning |
| --- | --- | --- |
| Hobby / bench / open-source dev board | SL 1 | Casual or coincidental violation |
| Commercial UAS, uncontrolled airspace, no payload of interest | SL 2 | Simple means, low resources, generic skills |
| Commercial/industrial vehicle, valuable cargo, contract work | SL 3 | Sophisticated means, moderate resources, IACS-specific skills |
| Defense, critical infrastructure, life-safety authority | SL 4 | Sophisticated means, extended resources, high motivation |

**Set SL-T at ideation.** It determines whether you need a secure element (cost, board area,
BOM line) or whether MCU-internal key storage suffices.  Discovering at QA that SL-T is 3
when the design supports SL-A 1 means a respin.

Record the triple explicitly: `SL-T = 3, SL-C = 2, SL-A = 2 → gap on FR1, FR3`.

## ISA/IEC 62443-4-1 — the process behind the board

Eight practices (REF-ISA-62443-4-1 [18]).  These are what an assessor asks for when they
want to know whether the board's security was designed or bolted on:

| Practice | Name | Artifact this skill expects |
| --- | --- | --- |
| SM | Security Management | Named security owner; SDLC doc |
| SR | Specification of Security Requirements | The control register with SL-T set |
| SD | Secure by Design | Threat model, attack surface analysis, defense-in-depth rationale |
| SI | Secure Implementation | Coding standard, static analysis results |
| SVV | Security Verification and Validation Testing | Test plan and results per control |
| DM | Management of Security-Related Issues | Vulnerability triage record |
| SUM | Security Update Management | Signed-update process, cadence, EOL policy |
| SG | Security Guidelines | The hardening/deployment guide shipped to the integrator |

**SG maps directly onto 213A's non-technical DO family and IR 8425's Documentation
capability.** Write it once, cite it three ways.

## Zone and conduit model at vehicle scale

62443 zones and conduits work on a vehicle as well as a plant.  A defensible partition for a
small UAS:

| Zone | Members | SL-T |
| --- | --- | --- |
| Flight-critical | Autopilot, ESCs, servos, IMU | Highest |
| Navigation | GNSS, magnetometer, air data | High |
| Payload | Cameras, sensors, third-party modules | Low — **treated as untrusted** |
| Ground link | Radio, telemetry modem | Medium — external attack surface |
| Maintenance | Debug, provisioning, config tooling | High — physical access assumed |

| Conduit | Between | Enforcement |
| --- | --- | --- |
| C1 | Flight-critical ↔ Navigation | Authenticated bus messaging |
| C2 | Flight-critical ↔ Payload | **Gateway PEP; one-way where possible** |
| C3 | Ground link ↔ Flight-critical | Authenticated, rate-limited, command-filtered |
| C4 | Maintenance ↔ everything | Physical presence + authenticated unlock, disabled in flight |

C2 is the highest-value control on most vehicles.  SP 800-207 §2.2 assumption 2 says devices
on the network may not be owned or configurable by you — the payload bay is exactly that.
A payload that can assert flight-critical bus messages is a design defect regardless of how
well the payload itself is built.

## ATT&CK for ICS — mapping board defects to adversary technique

Use these when writing findings, so a board-level defect connects to a real adversary
action.  Technique IDs from the MITRE ATT&CK for ICS matrix
(<https://attack.mitre.org/matrices/ics/>).

| Board defect | Enables (ATT&CK for ICS) | Control that closes it |
| --- | --- | --- |
| Unauthenticated bus command path | T0836 Modify Parameter; T0831 Manipulation of Control | SCA-IA-01, SCA-ZT-02 |
| Live debug port in production | T0839 Module Firmware; physical Initial Access | SCA-IA-04 |
| Unsigned firmware update | T0857 System Firmware; T0839 Module Firmware | SCA-SU-01 |
| No rate limiting / no resource bounds | T0814 Denial of Service; T0816 Device Restart/Shutdown | SCA-DS-03 |
| No integrity check on parameters | T0836 Modify Parameter | SCA-CFG-04 |
| Reachable from a non-flight zone | T0883 Internet-Accessible Device (analogue) | SCA-OT-02 |
| No logging of security events | Inhibits detection across all tactics | SCA-CS-01 |

Anchor severity to physical consequence, not CVSS alone.  A defect that permits T0831
Manipulation of Control on a flight actuator is Critical even if it requires physical
access, because the consequence is loss of aircraft.

Relevant tradecraft to cite when justifying a threat model: Stuxnet (PLC logic manipulation
with a valid-signature driver), TRITON/TRISIS (deliberate targeting of a **safety**
instrumented system), Industroyer/CRASHOVERRIDE (protocol-native ICS commands),
PIPEDREAM/INCONTROLLER (modular, cross-vendor ICS tooling).  TRITON is the one to raise when
someone argues the safety channel does not need security.
